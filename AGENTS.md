# AGENTS.md — guide for AIs and agents

This file is the entry point for any agent (Claude, Codex, Copilot, Cursor...) that will read, change or extend this repository. Read all of it before editing. The human-oriented chapters live in `docs/`; the material written for agents lives in `docs/ai/`. English is the canonical language of the project (interface, commands, public API, documentation and these instructions); see [Language](#language).

## What the project is

**Calamidade_Awakening** is a modular visual effects engine for Minecraft Java 1.21.1, NeoForge 21.1.267, Java 21, built on the **RimuLib 1.3.0** library (`FxApi` post-processing, `FilmApi` camera, menus). It synchronizes effect instances between server and clients, selects what to draw by priority and quality budget, and offers addons (other mods) a public API to register effects with a script (**Timeline**), scene mood (**Atmosphere**), their own shader passes, world meshes, camera, server gameplay cues and cards in the menu (Atlas and Focus). Since 0.9: beams (**Beam**), visual light on the world (**Light**) and protagonist priority (**HERO**). Since 0.10: **per-instance orientation** (`Placement`, yaw and pitch, following the anchor's body), **sources and limits** (`EffectSource`: player, mob, block, script; per-source limits and slots reserved for players in the server config; per-source cooldowns) and **ready-made triggers** (`EffectTriggers`: item, block entity, entity), plus a template for other mods to depend on the engine without Maven. Since 0.11: **Terrain API** (`TerrainShape`, `TerrainPalette`, `TerrainEdit`): craters, trenches and falling structures, written straight into the chunk sections at a Timeline marker (usually the impact frame's), with a burnt edge, real blocks in place of the stand-in, visual heat on the client, safety rules in the server config and undo. Outside the Terrain API the engine is cosmetic: damage and consequences come from the addons' cues, and Light does not change the game's light level.

Since 0.11.1, the Terrain API goes through NeoForge's explosion events (land-claim mods), the world border, spawn protection and the player's game mode, updates the outer shell of the edit and is covered by in-game tests in the repository (`./gradlew testGame` and `testClient`; Portuguese names `testeJogo` and `testeCliente`).

Since 0.11.2, measured quality profiles (LOW, BALANCED, HIGH and ULTRA, `QualityProfile`, caps in the client config with safety maxima), automatic quality **AUTO** (`AutoQuality`, the default) and the **Star Atlas as panels standing in the world** (`client/holo`, adapted from RespectCraft's holographic menu), the mod's only holographic panel, with tabs for abilities, quality, accessibility, terrain and diagnostics.

Since 0.12.0, **Sky API** (`Sky`, `Effects.sky`): sky layers by direction — black hole with gravitational lensing, portal to another galaxy, eclipse, rift, giant celestial body, aurora and distant lightning — painted in the engine's `sky` pass (first of the frame, outside the budget), which also hides the game's sun and moon; **global events** (`WorldEvents`: scopes AREA, DIMENSION and SERVER, late join, persistence, `/calamidade world`) and **per-dimension sky** (`SkyProfile`, `SkyProfiles`, `ProfileSkyEffects`: states with transitions, saved in the world). Chapter: [CEU-0.12.md](docs/CEU-0.12.md).

Since 0.13.0 (branch `claude/bosses-0.13`, release v0.13.0 published), **Boss API** (`Boss`, `Bosses`): a boss controller attached to an addon entity (phases, transitions by time, health, signal, damage, death and predicate, sequences through the Timeline, enter, exit and sustain effects, a global event per phase, optional invulnerability, persistence on the entity), **BossBar** (vanilla bar plus client styles `BossBars`, segmented bar, accessibility) and **Rig Anchors** (`RigAnchors`, `Point.socket`, `Effects.anchorSocket`, `AnchorCapture` on the client), without depending on GeckoLib. Chapter: [BOSSES-0.13.md](docs/BOSSES-0.13.md).

**0.14.0 Custom Sky — release candidate, not published**, integrated on top of 0.13.0 (Boss Engine) (original branch `claude/ceu-personalizado`): the Custom Sky Engine (0.14 Custom Sky and 0.15 Sky Objects & Cinematics, after 0.13 Bosses), additive only; architecture and checks in [CEU-PERSONALIZADO.md](docs/CEU-PERSONALIZADO.md). Phase 2 done: **Backdrop** (`Backdrop`, `Effects.backdrop`, `SkyProfile.StateBuilder.backdrop`): sky background from a 3 × 2 cubemap, a panorama or a gradient, drawn in `AFTER_SKY` without a post pass, composed with Atmosphere, eclipse, lens and the game's sun and moon; client option `customSkies`. Phase 3 done: **stars, constellations and nebulae** (`StarField`, `Nebula`, `SkyBlend`, `SkyDarkening`, `Effects.stars`, `Effects.nebulae`), batched in `AFTER_SKY`, with per-object composition (`NORMAL`, `LUMINOUS`, `COVER`) and a coverage layer read by the passes. Phase 4 done: **images, flipbooks and impostors** (`SkyImage`, `SkyImpostor`, `Effects.images`, `Effects.impostors`, `SkyProfile.StateBuilder.images/impostors`): any PNG as a billboard in the sky, spritesheets with `LOOP`/`ONCE`/`PING_PONG`/`TRACK` and the instance or world clock, pre-rendered 3D objects by views (with LOD), in the same batch and the same coverage layer as the stars, `layer(FRONT)` composed at the end of the `sky` pass; textures in the `SkyTextures` cache (one per PNG, asynchronous loading, memory and upload budgets per profile); tool `scripts/gerar_impostor.cjs`. The candidate has `BUILD = "release"` and the description without the development notice; publishing happens only through the workflow with the `v0.14.0` tag.

**0.15.0 Light Engine — experimental, not published** (branch `claude/great-pascal-pq0xtj`): light cookies, spotlights and projectors (phase 1), EMISSIVE/OVERRIDE blends, sharpness and high-resolution cookies (phase 2), adaptive light budgets with tiled lighting (phase 3), coverage first (phase 4: independent light lane and engine lights pass, spatial spread, density admission, temporal hysteresis, AUTO relief) and **phase 5**: final light/cookie budgets (LOW 32/24, BALANCED 80/60, HIGH 176/132, ULTRA 192/192), the "Reduced Visual Quality" notice for LOW, English as the canonical language (commands, Gradle tasks, docs) and rebranding preparation ([docs/REBRANDING.md](docs/REBRANDING.md)). Chapter: [LUZ-0.15.md](docs/LUZ-0.15.md). Formal GPU benchmarks of 0.15.0 are not complete.

Current version: last published release **0.13.0** (v0.13.0); in the build, engine **0.15.0** (experimental, not published; on top of the 0.14.0 candidate); example `examples/vfx-sample` **1.14.1** (depends on `[0.15.0,0.16.0)`). NeoForge 21.1.267 in the build; checked with 21.1.265 (`-Pneoforge.version=21.1.265`).

## Non-negotiable rules

1. **Public API.** Only `dev.calamidade_awakening.api.v1` (and `.client`) is API. Never remove a public member or change its signature: addons compiled against earlier versions must keep loading. To evolve, **add**: a new constructor keeping the old one, a record component with a compatibility constructor, a `default` method in an interface. Every public member needs Javadoc with units (ticks, blocks, 0..1), limits and, when it helps, a short example: the build fails without it. After changing the API, run `./gradlew apiDocs` and commit `docs/ai/API-REFERENCIA.md`. New public names (classes, methods, parameters, enum values) are English.
2. **Network.** Current channels: `event_v2` (0.10: orientation and source), `terrain_v1` (0.11: terrain edit state), `world_event_v1` and `world_end_v1` (0.12: global events), `sky_profile_v1` (0.12: sky state of a dimension), `boss_v1` (0.13: boss bar state beyond the vanilla bar), `live_v1` (0.15: list of each player's instances every 100 ticks, to reconcile lost ends), `end_effect`, `request_v2`, `release`. Changing or creating a packet requires a new engine version and the notice "server and clients on the same version" in `MUDANCAS.md` and in the release notes. No per-tick packets: the client derives everything from the instance clock (Timeline, Atmosphere, beams, lights, terrain edits, sky layers and sky profiles are registered on both sides); `terrain_v1`, `world_event_v1`, `sky_profile_v1` and `boss_v1` are sent once per state change and to whoever arrives later.
3. **Licenses and third parties.** Never commit third-party JARs or attach them to releases (`libs/*.jar` and `dist/*.jar` are in `.gitignore`; the experimental JARs of this project are force-added to `dist/` only when a phase asks for it). RimuLib is downloaded from CurseForge by the `rimulib` task and checked by SHA-256 (`gradle.properties`). Code from Minecraft, NeoForge and RimuLib is not copied here; use the APIs.
4. **Check with javap before using.** Every new type, method or field of RimuLib, NeoForge or Minecraft is checked in the JAR before its first use (names and signatures change between versions and the mappings are not those of your training):
   - RimuLib: `javap -p -cp libs/rimulib-1.3.0-neoforge.jar cyou.rimuru.rimulib.mc1211.client.api.FxApi\$Frame`
   - NeoForge and Minecraft: `javap -cp build/moddev/artifacts/neoforge-21.1.267-merged.jar net.minecraft.sounds.SoundEvents` (the file exists after the first build)
   - Use `javap -c` for behavior (for example, how the shader `#include` is resolved) and record new conclusions in `docs/VALIDACAO.md`.
5. **Git.** Run `git status` before every `git add` and add files by name. Never a blind `git add -A`, never commit `build/`, `run/`, `libs/*.jar`, `dist/*.jar` (except the experimental JARs a phase explicitly asks for, with `git add -f`). One commit per work step, with a message that says why.
6. **Terrain.** Only the Terrain API (`Effects.terrain`) replaces blocks from an effect: it applies the server rules (config `terrain`, dimensions, `mobGriefing`, `TerrainEditEvent`, since 0.11.1 world border, spawn, game mode and NeoForge's `ExplosionEvent`, tag `terrain_protected`, block entities only with an explicit option) and keeps the undo snapshot. Whoever changes the writer (`TerrainWriter`, `TerrainJob`, `TerrainBorder`) keeps what `LevelChunk.setBlockState` does (light through the same branch as vanilla, heightmaps, POI, saving) and runs `./gradlew testGame` and `testClient`. Do not write blocks in bulk in a cue with `level.setBlock` for a "crater": use the API. Reading the world outside the server thread is forbidden; the plan is pure precisely so it can run in parallel without reading the world.
7. **Accessibility.** Screen effects go through the methods of `AddonLayers.Post` (which apply intensity, shake, flashes and motion). Own passes that change the whole screen multiply their strength by `post.screenEffects()`, avoid flashing when `!post.flashAllowed()` and skip zoom/blur when `!post.motionEffects()`. Atmosphere exposure is already limited by the engine.
8. **Budget.** Do not bypass the per-frame budget (table below) or the Terrain API's blocks-per-tick budget (server config). Prefer analytic shaders (ray-box, ray-sphere, segments) over raymarching, and reduce steps when `post.quality() == LOW`.
9. **Version.** When changing the engine version, also change `version` in `src/main/resources/META-INF/neoforge.mods.toml`, the JAR the example uses in `examples/vfx-sample/build.gradle` and the range in the example's manifest; `checkModVersion` fails if they do not match. On release, update the version and SHA-256 of the JAR in `examples/consumidor/build.gradle` (the build is reproducible: the hash of the local `dist/` is the release's) and run `./gradlew syncRecipes`.
10. **Green build.** `./gradlew build` must pass at the end of every step, and so must the example (`./gradlew dist` and `./gradlew -p examples/vfx-sample build`).
11. **Choosing destruction.** Destruction does not automatically mean excavate + transform + fill. The Terrain API offers excavation (`carve`), shell transformation (`burn`), filling (`fill`) and structures (`structure`) as distinct operations; only `carve` and `commitAt` are required. A request for destruction does not, by itself, authorize filling, rebuilding or replacing large volumes of blocks: use `carve` without `burn`, `fill` or `structure` when the goal is to excavate (the engine still seals fluids and burns plants at the edge, for safety), and add transformation or filling only when the effect's intent asks for that result to **stay** in the world. What only needs to appear during the scene is visual (client heat, stand-in, beams, light, atmosphere, impact frame). For large or repeated attacks, weigh the real volume of changes, the chunks affected, the frequency and the concurrency, and consider visual alternatives before thinking about raising server limits. This guides the choice; it does not forbid complex effects when the developer wants them. Before creating complex destruction, read [Choosing the operation](docs/TERRENO-0.11.md#escolher-a-operação) and [Cost of a destruction](docs/TERRENO-0.11.md#custo-de-uma-destruição) (Portuguese chapter).
12. **Language and compatibility.** New user-facing text goes into `en_us.json` (canonical and fallback) through translatable components; never override the player's language. New commands, arguments, Gradle tasks, test names, reports and docs are English. Do not mass-rename internal identifiers, resource IDs, effect IDs, track names or file paths only for language: they are persistent or referenced (see [REBRANDING.md](docs/REBRANDING.md)). When an English name replaces a Portuguese command or task, keep the old one as a deprecated alias that delegates to the same implementation (`example.vfxsample.Cmd` for commands, `dependsOn` aliases in `build.gradle` for tasks). Do not change technical identity (mod ID, packages, namespace, payload or SavedData IDs, Maven coordinates) until a rebranding decision is explicitly made.

## How to create a new effect in 7 steps (the sky in 4b and the boss in 4c)

1. **Skeleton.** `python3 scripts/novo_efeito.py mymod solar_ray --project path/to/addon [--card]`. It generates the class (automatic registration in `FMLConstructModEvent`, command `/mymod effect solar_ray`), the shader and the translations. Alternative: copy the closest recipe from [docs/ai/receitas/](docs/ai/receitas/README.md).
2. **Script (Timeline).** Named phases for what happens, tracks for values that vary, markers for gameplay moments; `sustain` for ambient effects that only stop with `release()`. Chapter: [TIMELINE-0.7.md](docs/TIMELINE-0.7.md). Recipes: 1 (marker), 6 (sustain).
3. **Visuals.** Choose the right layer: beams (`Effects.beams`) and light on the world (`Effects.lights`) without a shader; scene mood (`Effects.atmosphere`); a post pass with your own shader (`AddonLayers.post` + `post.pass`, using `calamidade_fx.glsl`); a world mesh (`AddonLayers.world`); ready-made screen effects (`post.bloom`, `vignette`...). Main effect of the scene: `withPriority(Effects.Priority.HERO)`. Chapters: [FEIXES-0.9.md](docs/FEIXES-0.9.md), [LUZ-0.9.md](docs/LUZ-0.9.md), [LUZ-0.15.md](docs/LUZ-0.15.md) (cookies, spotlight, projector; experimental), [PRIORIDADE-0.9.md](docs/PRIORIDADE-0.9.md), [AVANCADO-0.6.md](docs/AVANCADO-0.6.md), [ATMOSFERA-0.8.md](docs/ATMOSFERA-0.8.md), [glsl.md](docs/ai/glsl.md). Recipes: 1 to 5 (shaders), 6 (mesh), 7 (atmosphere), 8 to 10 (beams), 11 and 12 (light), 13 (HERO), 28 (light lab).
4. **Terrain (optional, 0.11).** To dig: `Effects.terrain(id, TerrainEdit.carve(TerrainShape...).commitAt("impact").build())`, after the timeline; put the marker on the tick of the `Effects.Impact` (4 to 8 ticks of flash). Add `.burn(palette, thickness)` only if the surface should stay transformed, `.fill(...)` only if a real object should stay, `.structure(...)` only if a construction should stay (rule 11). Chapter: [TERRENO-0.11.md](docs/TERRENO-0.11.md), with the decision table and the costs. Recipes: 18 to 21 (use cases, not the minimum: all of them use `burn`).
4b. **Sky (optional, 0.12).** Black hole, portal, eclipse, rift, celestial body, aurora, distant lightning: `Effects.sky(id, Sky.blackHole().direction(az, el)...build())` after the timeline (up to 6 layers). For the whole server or a whole dimension, start the effect with `WorldEvents.start(id, Scope.SERVER, level, options)`; for the permanent sky of a dimension, `SkyProfiles`. Chapter: [CEU-0.12.md](docs/CEU-0.12.md). Recipes: 22 to 26.
4c. **Boss (optional, 0.13).** For a boss: `Bosses.define(Boss.builder(id).bar(...).phase(...).transition(...).build())` in the common constructor and `Bosses.attach(mob, id)` on the server when the addon decides; effects leaving the mouth or eyes with `Point.socket`/`socketAim` and `RigAnchors.define`, or the whole instance with `Effects.anchorSocket`. Chapter: [BOSSES-0.13.md](docs/BOSSES-0.13.md). Recipe: 27.
5. **Gameplay, camera and triggering.** Damage and consequences in `Effects.cue(id, "marker", ctx -> ...)` on the server (`ctx.forward()` and `ctx.facing(...)` give the instance direction); your own camera with `AddonLayers.film` aligned to the phases. To start the effect from an item, block or mob, use `EffectTriggers` (recipes 15 to 17); to turn it, `Placement` or `Effects.start(..., yaw, pitch)` and `Point.facing` points (recipe 14). Chapters: [GAMEPLAY-0.5.md](docs/GAMEPLAY-0.5.md), [AVANCADO-0.6.md](docs/AVANCADO-0.6.md), [INTEGRACAO-0.10.md](docs/INTEGRACAO-0.10.md).
6. **Accessibility and budget.** Reread rules 7 and 8 (and 11, if the effect touches terrain). Check `post.passesLeft()` before extra passes.
7. **Test.** `./gradlew build`, `./gradlew dist`, the addon build; `node scripts/previa_passes.cjs` to see beams and lights without the game; in game: the effect's command, **F7** (passes, vertices, HERO, beams, lights, atmosphere), **F8** on LOW/BALANCED/HIGH, screen effect intensity at 0, "hide flashes" on, and `/calamidade bench` for load. Full procedure: [TESTE-REAL.md](docs/TESTE-REAL.md). Record results in [VALIDACAO.md](docs/VALIDACAO.md).

## When to run each test (permanent rule, since 0.14 phase 3)

All existing tests stay in the repository, with the same coverage and the same tolerances; what changes is **how often** the same tests run. Launching Minecraft and rendering through llvmpipe is expensive: choose by the risk of the change.

| Moment | What to run |
|---|---|
| During implementation | Only what is fast and tied to the change: compilation, `checkBudget` (affected pure tests), `checkShaders` if you touched a shader, `checkApiCompat` if you touched the API, the affected preview composition test (`checkObjectComposition`, `checkBackdropComposition`) and the WebGL preview when it helps. Do not open Minecraft for every small change. |
| When a feature is done | Its integration tests, with the scenarios grouped into a single client launch whenever possible. |
| When a phase is done | One consolidated round of the regressions the phase may have affected, chosen by what changed: `checkSkyReference` if it touched sky, atmosphere or shaders; `testStars`, `testBackdrop` and `testSky` only if the phase changed the code they exercise; `testGame` only if it changed server, network, common registration, terrain or something else it covers (a change only to images or client shaders does not require it). |
| When a failure is found | Investigate and fix the case; run the affected test again; widen the round only if the fix can reach other subsystems. An infrastructure failure (Xvfb, download, timeout) does not justify repeating in a loop: record it and move on. |
| Before a release | The full battery required by the project, without shortcuts. |

A result already recorded in `docs/VALIDACAO.md` for the same relevant state of the code may be **reused**, and the record says so: separate what was executed in the session, what was reused (with the commit of the result) and what remains pending. Never change a test to hide a bug, never raise a tolerance to pass, never declare as executed what was only reused.

## Code conventions

- English Javadoc and code comments; English user-facing text in `en_us.json` (canonical and fallback; `pt_br.json` is an optional translation); English documentation, commit messages, commands, tasks and test output for new work. Older Portuguese docs, internal identifiers and the in-game test mod (`src/testeJogo`) are historical and are converted gradually, never by mass renaming of identifiers.
- Client coordinates: `post.center()` and shader uniforms are **relative to the camera** (the space of `scenePosAt`); `World` uses offsets from the instance center.
- fx shaders: RimuLib prepends `#version 150` and `common.glsl` (see [glsl.md](docs/ai/glsl.md)); write `fragColor` with the final scene color (read `DiffuseSampler`, add the effect, write everything).
- Registration order: `Effects.register` → `Effects.timeline` → `Effects.atmosphere` / `Effects.beams` → `Effects.lights` → `Effects.terrain` / `Effects.sky` → `Effects.cue`; sky profiles with `SkyProfiles.define` in the common constructor; cards with `Addons.publish` during mod construction; client layers in `FMLClientSetupEvent`. Triggers (`EffectTriggers`) may be `static final`: the effect only needs to be registered when they fire.
- Instance frame (0.10): Minecraft's local axes (`^x ^y ^z`): x to the left, y up, z forward; yaw 0 looks south, positive pitch looks down. Without orientation, the frame is the world axes (0.9 behavior).
- Calamidade **does not depend on GeckoLib** or other animation mods: rig code stays in the user's mod (see INTEGRACAO-0.10.md). Since 0.13, the addon reports a bone pose with `AnchorCapture.capture` in its own renderer; that pose is **visual only** and never goes back to the server (damage and collision use `RigAnchors.approximate`).
- Bosses (0.13): Calamidade never creates creatures, bars or events on its own; only `Bosses.attach` (called by the addon) creates a controller. Example boss attacks do not touch terrain; real destruction is optional, small, `carve` only and inside the Terrain API.
- New pure logic tests go into `checkBudget` (`src/test/java`, no JUnit).
- Terrain (0.11): shapes in the instance frame (x to the left, y up, z forward); a block is carved when the distance at its center is <= 0. The edge noise (`TerrainNoise`) is 32-bit integer arithmetic and has a faithful copy in `calamidade_terrain.glsl`: change one, change the other and the cases of `testar_glsl.cjs` (values taken from the Java).

## Language

English is the project's canonical language. `en_us.json` must contain every key (the build of a feature is not done until it does); other languages are optional and fall back to English. Do not override the player's Minecraft language. Portuguese command and task names remain as deprecated aliases; docs and examples recommend only the English names. Legitimate Portuguese leftovers: compatibility aliases, persistent identifiers (effect IDs such as `vfxsample:luz_runas`, sky state names, timeline track names, file paths), the historical in-game test mod and the optional `pt_br.json`.
